WebRTC Voice & Video Call Flow

Server acts as a signaling relay only — media streams flow peer-to-peer directly between browsers.

💡 Key Point: The server never sees media data. Socket.io only relays SDP (Session Description Protocol) offers/answers and ICE candidates for NAT traversal. Once the P2P handshake completes, all audio/video flows directly browser-to-browser.
📞
Caller
Browser A — creates SDP offer
Signaling via Socket.io
SDP Offer / Answer / ICE
📡 Socket.io Server
Once connected ↓
🎥 P2P Media Stream
Audio / Video direct
📲
Receiver
Browser B — creates SDP answer
1
Caller creates RTCPeerConnection + getUserMedia
Requests access to microphone/camera. Creates an SDP offer describing media capabilities (codecs, resolution).
2
emit call:initiate with SDP offer and metadata
{ targetUserId, sdp, callType: "video"|"audio", fromUserName, fromUserAvatar } — server relays to user:{targetUserId} room.
3
Receiver gets call:incoming — shows call UI
Can accept or decline. Accepting creates their RTCPeerConnection and generates SDP answer from the received offer.
4
emit call:accept with SDP answer → caller gets call:answered
Both sides set remote descriptions. The WebRTC handshake is now underway.
5
ICE candidates exchanged via call:ice-candidate
Both browsers gather network candidates (STUN/TURN). Relayed through Socket.io until the best P2P path is established via ICE negotiation.
6
P2P connected — media streams directly, server uninvolved
Audio/video flows browser-to-browser. Either side emits call:hangup to end → server relays call:ended.
💡 Group Call — Full Mesh Topology: Each participant establishes a direct P2P connection with every other participant. Server queries DB for all chat members and notifies them. N participants = N*(N-1)/2 P2P connections.
1
Initiator emits call:initiate-group with chatId
Server queries PostgreSQL for all members of that chat. Emits call:incoming-group to each member's user:{id} room — including chat title and initiator info.
2
Each joining member emits call:join-group
Triggers call:participant-joined broadcast to the chat room, prompting existing participants to initiate a new P2P connection to the new joiner.
3
Full Mesh: call:offer / call:answer between every pair
Each participant exchanges SDP with every other participant. Scales well for small groups (<5). For larger groups, an SFU/MCU media server would be the next step.
4
Leaving: call:leave-group → call:participant-left
Remaining participants close their RTCPeerConnection to the departed peer and update UI accordingly.

Dual Encryption Strategy

Two modes of AES-256-CBC — deterministic for queryable emails, random IV for pattern-proof messages.

🔒 Deterministic Encryption
Used for: User Emails — AES-256-CBC with Static IV
🔑
Key derived at startup via scrypt (memory-hard KDF) from JWT_SECRET
KEY = crypto.scryptSync(JWT_SECRET, "salt-for-db-encryption", 32)
↓
📍
Static IV — 16 zero bytes. Same IV every call means same plaintext always → same ciphertext.
STATIC_IV = Buffer.alloc(16, 0) // 0x000...000
↓
✅
Why this enables DB queries: Same email always produces same ciphertext, so DB can enforce UNIQUE constraint and run exact-match WHERE queries.
"user@mail.com" → "X7kLmQABC+=" (always the same)
DB: WHERE email = encryptDeterministic(input)
🎲 Non-Deterministic Encryption
Used for: Message Content — AES-256-CBC with Random IV
🔑
Same scrypt-derived key — but a brand new random IV is generated for every single message.
KEY = same 32-byte scrypt-derived key
↓
🎲
Random IV — 16 cryptographically random bytes per encryption call. Stored prepended to ciphertext.
iv = crypto.randomBytes(16) // different every time
stored: IV_hex + ":" + cipher_hex
↓
🛠
Why this protects messages: Same message sent twice produces completely different ciphertexts — breaks ciphertext pattern analysis (IND-CPA security).
"Hello!" → "a3f2c8...:9d7e1a..." (different every time)
PropertyEmails (Deterministic)Messages (Non-Deterministic)
Initialization VectorStatic zeros (16 bytes)Random 16 bytes each time
Same input → same output?Yes — required for DB lookupNo — different ciphertext each time
Security goalQueryability & uniqueness enforcementIND-CPA — hides message patterns
AlgorithmAES-256-CBCAES-256-CBC
Key derivationcrypto.scryptSync(JWT_SECRET, "salt-for-db-encryption", 32)

Presence System — Online / Offline

Redis-powered with multi-tab support. Users stay "online" until their last tab closes.

🔗 User Connects
Increment connection counter
INCR user:conn_count:{userId}
Only if count == 1 (first tab) → mark online in set
SADD online_users {userId}
Fetch all chat partners from DB (cached in Redis)
GET user:partners:{userId} // or query ChatMember
Notify all partners of online status
io.to("user:{partnerId}").emit("presence:change", { status: "online" })
Send current partner statuses to this new socket
SISMEMBER online_users {partnerId} // for each partner
🔌 User Disconnects
Decrement connection counter
DECR user:conn_count:{userId}
Only if count <= 0 (last tab) → mark offline
SREM online_users {userId}
Record last-seen timestamp in Redis
SET user:last_seen:{userId} = new Date().toISOString()
Notify all partners with lastSeen timestamp
emit("presence:change", { status: "offline", lastSeen })
